# Видеоролики AVI

В главном меню действует «Вступление»: `movies/intro.avi` читается через тот же `AssetCatalog`, что модели и текстуры. Esc, Enter, пробел или новая левая кнопка мыши пропускают ролик. После окончания или ошибки приложение возвращается в главное меню; ошибка появляется в нижней строке. Ctrl+X завершает приложение.

## Ресурсы и замены

Приоритет: GUT → отдельный файл Data → overrides. Для замены вступления положи AVI по пути `movies/intro.avi` внутри каталога замен. Регистр и Windows-разделители нормализуются. Новый движок не вызывает оригинальный EXE или системные Windows-кодеки; пользователю не нужен FFmpeg.

Текущий профиль — **MJPEG (MJPG) + необязательный PCM16LE, mono/stereo**. Все 17 роликов восстановленной установки используют эти кодеки. Это уже обработанный комплект ресурсов; ролики нетронутого диска не проверены. Indeo, Cinepak, MPEG-4, MP3/ADPCM, несколько видеопотоков и ненулевой `dwStart` пока возвращают понятную ошибку. Расширение `.avi` само по себе не определяет кодек.

Окно и интерфейс остаются HD+ и поддерживают 16:9/21:9. Видео масштабируется с сохранением пропорций, помещается целиком в окно и центрируется на чёрном фоне. Старый ролик 640×480 не меняет разрешение окна; вокруг изображения могут быть поля. Для полного заполнения широкого экрана можно поставить широкую замену ролика. Изображение не растягивается и сюжетные края не обрезаются.

## Как работает проигрыватель

`shadow-formats/src/avi.rs` проверяет границы RIFF/LIST, выравнивание нечётных чанков, упорядоченные `strl`, вложенные `rec ` и продолжения AVIX. Видео хранится как диапазоны JPEG внутри одного `Arc<[u8]>`; пустой видеоблок повторяет предыдущий кадр. PCM-итератор читает little-endian i16 непосредственно из диапазонов аудиочанков и переводит их в f32 для Bevy, сохраняя порядок L/R.

`shadow-model-viewer/src/movie.rs` готовит файл и первый кадр в `AsyncComputeTaskPool`. Далее JPEG декодирует отдельный поток Rust, чтобы не ждать занятый общий пул Bevy. Две очереди `sync_channel(1)` и признак занятости допускают только один ожидающий кадр. При отставании выбирается кадр текущего времени; очередь всего фильма не создаётся. Размер JPEG проверяется до декодирования и должен совпадать с AVI. Файл читается целиком в сжатом виде, поэтому это ещё не потоковое чтение с диска. Пределы прототипа: файл 512 МиБ, сжатый кадр 32 МиБ, не более 8192 по каждой оси и 16 777 216 пикселей, частота до 240 fps, длительность до суток.

PCM зарегистрирован как собственный Bevy `Decodable`/`Source` через `AddAudioSource`. Звук подготовлен на паузе и запускается вместе с временной шкалой изображения. В норме `AudioSink::position()` задаёт кадр. Если звук короче видео, оставшееся видео продолжается по времени; последний видеокадр сохраняется до конца более длинной дорожки. Без аудиоустройства после короткого ожидания начинается показ без звука. Зависшая позиция устройства тоже не удерживает экран навечно. Это не обещание покадровой синхронизации аппаратного аудиовыхода: задержка устройства и пропуск кадров при слабом CPU ещё требуют пользовательской проверки.

При выходе из состояния `Movie` останавливается sink, удаляются аудиосущность, изображение, аудиоasset и ресурсы задач. Закрытие очередей останавливает поток декодирования после текущего кадра без ожидания в главном потоке. UI удаляется через `DespawnOnExit`. Повторный вход создаёт новое воспроизведение с начала.

Основа формата: [Microsoft AVI RIFF File Reference](https://learn.microsoft.com/en-us/windows/win32/directshow/avi-riff-file-reference). Собственный источник звука следует [официальному примеру Bevy](https://bevy.org/examples/audio/decodable/) и API закреплённой версии Bevy 0.20.0.

## Диагностика

Из корня проекта:

```bash
# Обычное воспроизведение любого поддерживаемого ролика:
./scripts/demo-game.sh "" "" --movie movies/vtc100.avi

# Сведения о потоках, PCM SHA-256 и PNG первого/среднего/последнего кадра:
./scripts/demo-game.sh "" "" --movie movies/intro.avi --movie-json /tmp/intro.json

# Неподвижный кадр на отметке 25 секунд в широком окне:
./scripts/demo-game.sh "" "" --movie movies/intro.avi --movie-time 25 \
  --window 1680x720 --screenshot /tmp/intro.png

# Пропуск, повтор, естественное окончание и освобождение ресурсов:
# Для быстрого прогона укажи короткий тестовый ролик в overrides.
./scripts/demo-game.sh "" "/путь/к/заменам" \
  --movie movies/intro.avi --movie-smoke-json /tmp/movie-smoke.json
```

Для снимка звук отключён и видеовремя зафиксировано. `--movie-time` допустим только вместе со снимком. В тестах вывода live-ввод игнорируется. Windows/macOS используют тот же код, но нативная проверка этих ОС ещё не выполнена.

## Изучение Rust

Сначала открой `AviMovie`: `Vec<u8>` получает байты, `Arc<[u8]>` разделяет владение, `Range<usize>` описывает кадр без копирования. Затем проследи `PcmSamples::next`: один i16 превращается в f32, а переход между чанками не меняет порядок отсчётов. В `movie.rs` сравни эту обычную структуру с обёрткой `Decoder`, которая дополнительно сообщает Bevy частоту и число каналов.

Проследи подготовку `Task → poll_once`, затем `sync_channel → try_recv → Assets<Image> → ImageNode`. Здесь главное окно не ждёт JPEG-декодер. Упражнение: объясни, почему ожидающий кадр только один и почему при отставании не нужно последовательно показывать все пропущенные кадры. Затем запусти ролик, пропусти его и найди, какие сильные ссылки удаляет `cleanup`.
